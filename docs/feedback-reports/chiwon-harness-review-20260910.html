2. 하네스 · 잘 된 부분

중단(interrupt) 처리 코드 확인
agent.ts:290-311 — 중단 시 응답을 받지 못한 tool call마다 합성 에러 결과를 채워 넣는다. 이걸 빠뜨리면 다음 사용자 입력에서 제공자의 tool-call 규약이 깨져 요청이 그대로 실패한다. 여기까지 처리한 구현은 흔치 않다.
압축 실패 모드 방어 코드 확인
  • 툴 호출 쌍이 모두 닫힌 경계에서만 자른다 — context-manager.ts:63-75
  • 요약 API 실패에도 resume 가능하도록 요약 전에 먼저 저장 — agent.ts:145-146
  • 요약이 원본보다 크면 적용 거부 — context-manager.ts:93-95
  • 요약 대기 중 대화가 바뀌면 덮어쓰지 않음 — context-manager.ts:99-101
  • 압축 후에도 예산 초과면 루프 대신 throw — agent.ts:184-186
마지막 판단이 특히 맞다. 요약을 반복하면 조용히 정보만 잃는다.
제공자 경계와 replayState 코드 확인
제공자 필드명이 adapters/ 밖으로 새지 않는다. 원본 assistant 블록 재사용은 adapter·provider·model·공통 content 해시 4개가 모두 일치할 때만 허용한다 — anthropic-messages.ts:66-77. reasoning 원문 재전송을 이 정도로 방어적으로 다룬 건 좋다.
추정치를 실측으로 교정한 이력 코드 확인
이미지 토큰 추정을 장당 4,000 → 전송크기/750으로 바꿨다 — token-budget.ts:25-30. dev-log에 “4,000은 실측의 7배여서 압축이 실제 사용량 26~46k에서 발동하고 플레이 중 게임 시간이 1~3초 통제 없이 흘렀다”는 근거까지 남아 있다. 이 프로젝트에 측정 루프가 있다는 증거라서, 개별 기능보다 이게 더 좋은 신호다.
계층 분리가 실제로 성립 실행 검증
my-first-harness.ts만 argv/env를 읽고 나머지는 주입받는다. 코어가 UI를 모르고 이벤트만 낸다. CLI/TUI 교체가 말뿐이 아니라 실제로 동작하는 것을 두 모드 부팅으로 확인했다.

3. 하네스 · 지적 사항 6건

A. 프롬프트 캐싱을 측정만 하고 요청하지 않는다 영향 큼

adapters/usage.ts:15-22는 cache_read_input_tokens와 cache_creation_input_tokens를 정확히 파싱한다. 그런데 anthropic-messages.ts:146-154의 요청 본문에 cache_control이 하나도 없다. Anthropic은 명시적 breakpoint가 없으면 캐시가 동작하지 않으므로, 측정 코드가 항상 0을 읽고 있을 것이다. 스텝마다 전체 대화를 재전송하는 구조라 Haiku 세션은 입력 토큰을 매 스텝 풀로 낸다.

먼저, 프리픽스 위생은 오히려 좋다 코드 확인
시스템 프롬프트에 날짜·타임스탬프처럼 매 호출 변하는 값이 하나도 없다(prompts.ts 전량 정적). 스킬 카탈로그는 {name, description, location}만, MCP 툴 이름 목록도 sort()로 순서 고정(tool-manager.ts:70). AGENTS.md를 첫 user 메시지로 올린 배치(agent.ts:135-136)도 캐시 관점에선 정답이다 — 고정 텍스트가 system 바로 뒤에 붙어 frozen 프리픽스가 그만큼 길어진다.
실제로 프리픽스를 깨는 것 ① — modeInstructions(mode)가 system 안에 있다(agent.ts:132). 그리고 plan 승인 시 모드가 턴 도중 스텝 경계에서 바뀐다(agent.ts:216-220). PLAN_INSTRUCTIONS(1,189자) → EDIT_INSTRUCTIONS(342자)로 system 텍스트가 달라지므로, plan을 승인하는 순간 tools+system 프리픽스가 깨지고 뒤의 messages까지 전부 무효화된다.
→ 모드 지침을 메시지 배열 끝쪽 하네스 알림으로 내리면 system+tools가 세션 내내 고정된다. [하네스 알림] 라벨 규약이 이미 있어 자리는 마련돼 있다.
실제로 프리픽스를 깨는 것 ② — getModelDefinitions가 발견된 MCP 툴을 넣고 sort()로 재정렬한다(tool-manager.ts:75-80). 새 툴이 배열 중간에 삽입되므로 append-only도 아니고, tools가 제일 앞에 렌더되니 ToolSearch 한 번 = 전체 캐시 무효다. 점진 공개의 구조적 대가라 없앨 일은 아니고, ToolSearch를 초반에 몰아서 끝내면 이득이 크다는 것을 스킬/프롬프트에 명시해두는 편이 현실적이다. 같은 이유로 /mcp 토글도 프리픽스를 깬다.
breakpoint를 어디에 걸어야 하나 — 4,096 경계 주의

Haiku는 최소 캐시 프리픽스가 있고, 그보다 짧으면 마커가 있어도 조용히 no-op이다(에러도 안 난다). 같은 사내 과제에서 system 3,913 토큰으로 이 경계에 걸려 캐싱이 무효였던 실측 사례가 있다. 이 하네스의 프리픽스를 세어보면:

BASE_SYSTEM_PROMPT        3,150자  ≈   787 토큰
PLAN/EDIT 모드 지침     342~1,189자  ≈  85~297 토큰
내장 툴 description 합계  4,171자  ≈ 1,042 토큰   ← 스키마 JSON 제외, 하한
+ 스킬 카탈로그, MCP 툴 이름 33개(memory 9 + playwright 24)

스키마 JSON까지 합치면 3,500~5,000 토큰 언저리로 경계선 근처다. 그래서 “system에 breakpoint 하나”가 아니라 AGENTS.md 마지막 블록에 거는 것이 안전하다 — tools+system+AGENTS.md를 한 번에 덮으면서 최소 길이를 확실히 넘긴다. 넣은 뒤 usage.cachedInputTokens가 실제로 0이 아닌지 확인하는 것까지가 한 세트이고, 그 측정 배관은 이미 깔려 있다. 확인 필요 모델별 최소 프리픽스 값은 현재 공식 문서로 확인할 것.

B. 한국어 토큰 추정이 실측되지 않았다 영향 큼

token-budget.ts:19-23:

export function estimateTextTokens(text: string): number {
  let tokens = 0;
  for (const char of text) tokens += char.codePointAt(0)! <= 127 ? 0.25 : 2;
  return Math.ceil(tokens);
}

ASCII 0.25/자 vs 비ASCII 2/코드포인트 — 8배 비대칭이다. 이 하네스는 시스템 프롬프트·에러 메시지·AGENTS.md·모델 출력이 전부 한국어라 이 값이 추정 전체를 지배한다. 과대추정이면 압축이 필요 이상으로 일찍 발동해서 원문을 조기에 잃는다.

이미지에서 7배 오차를 잡아낸 것과 정확히 같은 작업이 텍스트에는 아직 적용되지 않았다. usage.inputTokens를 이미 JSONL에 기록 중이므로 estimate vs 실제 input_tokens 회귀 한 번이면 계수가 나온다. 이 목록에서 가장 저비용·고효과 항목이다.

C. step 하나에 assembleContext()를 최대 4번 호출한다 중간

agent.ts 172 · 181 · 183 · 188행. 즉 모델 호출 1회당 컨텍스트 조립 4회다. 그리고 조립마다 projectRequestImages가 돌면서 이미지별로 SHA-256을 다시 뜨고(image-request.ts:9-11), 캐시 미스면 sharp 리사이즈까지 한다(77-90).

previews 캐시는 16개이고, 히트해도 재삽입하지 않아 LRU가 아니라 FIFO다(image-request.ts:74, 86). 게임 테스트처럼 gameTestObserve 스크린샷이 계속 쌓이는 세션은 17장째부터 모델 호출마다 전량 재인코딩 × 4회가 된다. 임계 판정용으로 만든 request를 재사용하면 대부분 사라진다.

D. test-run.ts의 abort 리스너 누적 낮음

game-testing/test-run.ts:236(키별 대기)과 92(waitGameTime)에서 signal.addEventListener("abort", …, {once:true})를 달지만 정상 완료 시 제거하지 않는다. {once:true}는 발화해야 정리된다.

# 한 턴에서 gameTestAct 30회 × 입력 4개 시나리오 재현
정상 완료 후에도 남아있는 abort 리스너 수: 120

실행 검증 Node 24는 AbortSignal에 MaxListenersExceededWarning도 띄우지 않아 조용히 쌓인다. 메모리 영향은 작지만 중단 시 전부 발화하고, {once:true}가 알아서 치워줄 거라 착각하기 쉬운 자리다.

E. check() 주석이 코드와 다르다 낮음

test-run.ts:182에 “확인 전 상태로 돌려놓는다”고 되어 있지만, 복구되는 것은 running/paused 모드뿐이다. advance(CHECK_ADVANCE_MS)(189행)로 흐른 게임 시간 500ms는 되돌아가지 않고, 조각이 실제로 떨어진 뒤 플레이가 시작된다. AGENTS.md가 “코드가 바뀌면 주석도 함께 맞춘다”를 규칙으로 두고 있어 더 눈에 띈다.

F. SSE — 남은 것은 파서가 아니라 채널이다 중간

스레드에서 “SSE 한번 해보세요”라는 피드백이 있었는데, 현재 상태를 정확히 하면:

  • adapters/responses-stream.ts는 SSE를 이미 파싱한다 — 프레임 경계, [DONE], response.output_item.done 순서 검증까지 되어 있다.
  • 다만 readResponsesStream은 완료까지 모아서 JSON 응답과 같은 형태로 반환한다(49-53행). http.ts:24의 onEvent도 기록용 배열에 push만 한다.
  • 즉 전송 계층 SSE는 됐고, 사용자에게 흘려보내는 스트리밍이 안 된 것이다.
남은 작업은 파서가 아니라 채널이다. LLMAdapter.generate가 Promise<result>만 반환하는 구조라 delta를 agent → UI로 보낼 통로 자체가 없다. generate(request, observer, signal, onDelta?) 하나와 AgentEvent에 assistant-delta를 추가하면 tui.ts는 이미 이벤트 구독형이라 그대로 붙는다. 어댑터 3개 중 delta가 있는 건 Responses뿐이니 나머지는 완료 시 1회 방출로 맞춰도 된다.
부수 효과가 더 크다 — 지금은 응답이 끝나야 Esc가 의미 있어진다. delta가 들어오면 턴 중간 중단이 실제로 빨라진다.

덧 — 실행해보고 추가로 확인한 것

  • 키가 없어도 TUI가 끝까지 부팅된다. 어댑터가 키를 generate 시점에만 검사한다(anthropic-messages.ts:141). MCP 33개를 연결하고 세션 ID까지 발급한 다음, 첫 메시지를 보내는 순간에야 실패한다. 시작 시 경고 한 줄이 있으면 좋겠다. 실행 검증
  • README와 실제가 어긋난다. README는 pnpm install인데 pnpm이 devEngines로만 선언돼 있어 미설치 환경에선 corepack pnpm install이 필요하다. 본문은 “Node.js 24 이상”, 전역 설치 절은 “Node.js 26에서 검증”으로 표기가 갈린다. 사소하지만 첫 실행에서 걸린다. 실행 검증

lines= 9 → 95%      lines=19 → 95%
lines=20 → 05%
즉 레벨 진행도의 중복 표시인데, UI 문구는 “모듈을 정렬하면 안정도가 올라갑니다”라서 다른 지표처럼 보인다. 위 스크린샷이 결정적이다 — 보드가 천장까지 차서 죽는 순간에 05%, 반대로 9줄 지운 직후엔 95%. 302점을 내고 8조각을 쌓은 상태에서도 05% 고정이었다.
→ 심해 관측소 컨셉의 핵심 계기판인데 내용이 비어 있다. 보드 최고 높이나 구멍 개수 같은 실제 위험도를 넣으면 컨셉과 게임 로직이 처음으로 연결된다. 이건 버그 수정이라기보다 가장 값싼 완성도 상승이다.
③ lock delay가 없다 실행 검증
soft()가 아래로 못 가는 순간 즉시 lock()한다. 바닥에 닿는 프레임에 merge되므로 착지 후 좌우 이동·회전 슬라이드가 원천 불가능하다. 컨셉 완성도보다 이게 체감을 제일 많이 깎는다.
덧: 스레드에서 언급된 “플레이 실력이 아직 나쁨”이 모델만의 문제가 아닐 수 있다. 게임 쪽에서 착지 후 조정을 아예 허용하지 않는 것도 절반쯤 원인이다.
④ 일시정지 중에도 게임 시계가 계속 간다 실행 검증
startedAt이 begin()에서만 설정되고 pause 보정이 없다. 표시는 멈춰 보이지만 내부는 Date.now()로 계속 센다. 
정지 전 00:01 → (P로 정지, 5초 대기) 화면 00:01 → (P로 재개, 1.1초) 00:07
정지한 5초가 그대로 기록에 남아 재개하는 순간 점프한다.
⑤ 게임오버 오버레이 문구가 복구되지 않는다 실행 검증
gameOver()가 kicker/h1/p/버튼 텍스트를 파괴적으로 덮어쓰는데 begin()이 복구하지 않는다. 재시작(R) 후에도 station signal lost / “수압이 한계를 넘었습니다.” / “다시 관측”이 그대로다. 첫 게임오버 이후 초기 “압력 균형을 맞추세요” 화면으로 영구히 돌아갈 수 없다.

그 외 코드 확인

  • 회전 킥이 좌우 ±1, ±2뿐이다. 바닥 킥이 없어 I조각을 바닥 근처에서 세울 수 없고 T-spin도 불가능하다.
  • 홀드 없음, next 미리보기 1개.
  • clearLines()의 outer: 라벨은 사용되지 않는 죽은 코드다.

③~⑥은 LLM이 생성한 테트리스의 전형적인 누락 세트다. 원래 목표가 “하네스가 자기가 만든 걸 플레이해서 잡아내는 것”이었는데, 현재 플레이 루프로는 이걸 잡을 수 없다. 그래서 다음 절이 이 리뷰의 핵심이다.

5. 두 산출물을 잇는 지점 — 관측을 텍스트로

스레드의 “이미지 인식 말고 데이터화해서 순수 텍스트로” 피드백이 코드에서 정확히 어디에 놓이는지 따라가 봤다.

계층현재 상태
gameTestObserve스크린샷 PNG + 메타데이터만 반환. 게임 상태 텍스트 없음 — tools/game-testing.ts:96-105
브리지 명령tabs / install / runFor / resume / keydown / keyup / screenshot 7개뿐. DOM·JS를 읽는 명령이 아예 없다 — bridge.ts:8-17, mcp-controller.cjs:45-70
게임 쪽board가 클로저 변수이고 전부 <canvas>로만 렌더된다. DOM에 상태가 하나도 없어 browser_snapshot으로도 안 보인다
→ 텍스트화는 한쪽만 고쳐서는 안 되고 양쪽에 계약이 필요하다
  1. 컨트롤러에 evaluate 명령 추가. mcp-controller.cjs:57에 이미 page.evaluate가 있지만 그건 clock이 pauseAt되기 전이다. pause 상태에서도 걸리지 않는지 10줄 PoC로 먼저 확인해야 한다. 계획서 1안이 교착났던 원인은 MCP의 settle 대기였지 evaluate 자체는 아니었으니 될 가능성이 높지만, 확인 전엔 가정하지 않는 게 이 프로젝트의 방식이다. 확인 필요
  2. 게임 쪽 관측 계약. window.__observe = () => ({ board, current:{type,x,y,rot}, next, score, lines, gameOver }). 테트리스는 200자면 충분하다.
  3. gameTestObserve에 format: "text" | "image" | "both". 관측당 약 440 이미지 토큰이 수백 자로 떨어진다. 그런데 진짜 이득은 토큰이 아니다 — L(관찰→입력 지연)이 줄어 rate = H / L이 1에 가까워진다. 현재 rate 0.048은 게임 시간을 20배 늘려놓고 재는 것이므로, 텍스트화하면 이 왜곡 자체가 사라진다. 스킬이 “Slowed-clock success is not normal-speed success”라고 스스로 경고하는 그 간극이 좁혀지는 것이다.
  4. 조작도 한 단계 올린다. gameTestPlace({ column, rotation }) 같은 배치 단위 액션. 현재 gameTestAct는 키 시퀀스라 조각 하나에 이동 횟수만큼 계획이 필요한데, 배치 단위면 한 모델 호출 = 한 조각이라 한 판이 수천 호출에서 50~100 호출로 떨어진다. 스레드의 “턴제로 바꿔도 괜찮다 / 내릴 위치와 회전을 입력받도록”이 정확히 여기 해당한다.
규칙 하나를 같이 손봐야 한다. SKILL.md의 “Do not read or modify the game's internal state to make a check pass”와 텍스트 관측이 충돌한다. 읽기는 관측 / 쓰기는 치팅으로 규칙을 쪼개고, 그와 별개로 “화면에 보이지 않는 것을 읽어서 통과시키는 것”은 금지로 남겨야 한다. 안 그러면 위의 ②(게이지가 실제 상태와 무관) 같은 표시·렌더링 버그를 영영 못 잡는다. 그래서 텍스트 관측을 넣더라도 최종 확인 한 번은 이미지로 남기는 편이 맞다고 본다.
