my-first-harness 피드백

저장소를 읽고, 로컬에 설치해 실제로 돌려 본 뒤 정리했습니다. 기능 유무는 소스로 확인했고, 캐싱과 스트리밍 두 가지는 실제 모델 호출로 측정했습니다. 2026-09-09 커밋(a6af095) 기준입니다.

추가할 것으로 꼽은 항목 중 스트리밍 화면 출력과 프롬프트 캐싱은 개발 로그에 이미 범위 밖으로 적어두신 것들입니다. 새로 지적한다기보다 다음 우선순위에 대한 의견으로 봐주시면 됩니다.

잘된 점

1. 컨텍스트 압축 트리거를 매 호출마다 다시 잽니다

agent.ts의 step()이 LLM 호출 전마다 shouldCompact(await assembleContext(session))로 이번에 실제로 보낼 요청을 조립해서 크기를 잽니다.

직전 응답의 usage 값을 재사용하는 방식도 가능한데, 그 경우 사용자 턴이 바뀌면서 값이 초기화돼 새 턴의 첫 요청만 검사 없이 나가게 됩니다. 긴 대화를 이어가거나 큰 세션을 /resume 할 때 첫 요청이 컨텍스트 초과로 실패하는 형태로 드러나고, 재현 조건이 턴 경계라 눈에 잘 띄지 않습니다. 매번 실제 요청을 재기 때문에 이 경로가 생기지 않습니다.

초과 시에는 3단으로 내려갑니다 — ① 툴 결과 프루닝 → ② 오래된 구간 요약 → ③ 그래도 넘으면 명시적 에러. 마지막 단계 덕분에, 고정 지침과 툴 정의만으로 예산이 찬 상황에서 요약을 무한 반복하지 않고 원인을 사용자에게 돌려줍니다.

2. 컨텍스트 예산을 모델별로 분리했습니다

token-budget.ts의 contextWindow / reservedOutputTokens / safetyMarginTokens / retainRatio를 연결마다 따로 둡니다. 단일 임계값 하나를 쓸 때보다, 컨텍스트 한도가 크게 다른 모델을 섞어 쓸 때 동작이 달라집니다.

이미지 토큰 추정도 전송 크기 기반(가로×세로/750)으로 바뀌어 있고, 장당 4,000으로 잡았을 때 압축이 너무 일찍 발동했다는 교정 경위가 주석에 남아 있습니다.

3. 테스트가 본문보다 많고 실서버 검증이 분리돼 있습니다

본문 4,923줄에 테스트 7,161줄입니다. 받아서 그대로 돌렸을 때 타입 에러 0, 테스트 245개 전부 통과했고 네트워크는 타지 않았습니다.

실제 서버·모델을 쓰는 검증(test:farm / test:anthropic / test:mcp / test:playwright)은 기본 테스트와 분리돼 있습니다. "--model이 붙는 것은 유료"라고 README에 명시돼 있어, 비용이 드는 경로를 의도치 않게 밟을 여지가 줄어듭니다.

4. 실행 기록에 API 원문을 남깁니다

execution-history가 메시지뿐 아니라 API 요청/응답 원문과 사용량을 JSONL로 보존합니다. 와이어 레벨 문제가 생겼을 때 재현 없이 바로 확인할 수 있습니다. 이번 피드백의 사용량 확인도 이 기록으로 했습니다.

5. SSE 파서가 경계 조건을 처리합니다

adapters/responses-stream.ts가 CRLF 경계, UTF-8 멀티바이트 조각 이어붙이기, 여러 줄에 걸친 data: 필드, : 로 시작하는 keepalive 주석 무시를 모두 처리합니다. 직접 구현할 때 놓치기 쉬운 항목들입니다.

readResponsesStream()의 "delta만으로 툴을 실행하지 않는다"는 주석도, 툴 인자 JSON이 델타로 쪼개져 온다는 점을 고려하면 타당한 선택으로 보입니다.

6. MCP 툴을 이름만 먼저 넣고 정의는 나중에 펼칩니다

MCP 툴 이름 목록만 컨텍스트에 넣고 ToolSearch로 정의를 점진 공개합니다. 설치해 보니 memory 9개 + playwright 24개가 붙는데, 정의를 전부 미리 실으면 그만큼 컨텍스트를 차지합니다. 연결하는 서버가 늘어날수록 차이가 커지는 구조입니다.

추가하면 좋을 점

1. SSE 증분을 화면까지 연결하기

파서는 이미 동작하므로 남은 것은 연결입니다.

스트리밍 연결로 60줄짜리 답변을 요청하고, 델타 도착 시각과 generate() 반환 시각을 같이 쟀습니다.

+0.00s  generate() 호출
+1.20s  HTTP 200  content-type=text/plain; charset=UTF-8
+1.55s  ← 첫 델타 도착 (response.output_text.delta)
+3.90s  generate() 반환 — 여기서야 화면에 글자를 쓸 수 있다

델타 119개 수신 / 첫 델타 → 반환까지 2.35초

델타는 119개가 정상적으로 들어옵니다. 다만 adapters/http.ts의 onEvent가 events.push(event)로 배열에 쌓기만 하고, observer.onResponse는 finally에서 스트림이 다 끝난 뒤 불립니다. 그래서 2.35초 동안 텍스트는 메모리에 있는데 화면은 비어 있습니다. 170자 답변 기준이고, 2,000자 답변이면 같은 비율로 늘어납니다.

작업은 onEvent를 실행 기록 수집용으로만 쓰지 말고 에이전트 이벤트로 승격시켜 CLI/TUI까지 전달하는 것입니다. 코어는 이벤트만 내고 화면은 바꿔 끼우는 구조가 이미 있어서 붙일 자리는 있습니다. 툴 인자를 완성 후에 실행하는 현재 원칙은 그대로 두는 편이 맞습니다.

2. Anthropic 경로에 프롬프트 캐시 마커 붙이기

실제 툴 정의 13개를 실은 동일 요청을 Haiku로 연속 2회 보내고, 보낸 본문과 받은 사용량을 확인했습니다.

회차 본문의 cache_control system 타입 input cache_write cache_read
1 0회 string 4,789 0 0
2 0회 string 4,789 0 0

Responses / Chat Completions 경로는 서버가 캐싱하지만, Anthropic Messages는 cache_control: {type: "ephemeral"} 마커를 붙여야 캐시가 생깁니다. 지금은 system이 평문 문자열로 나가고 있어 두 번째 호출도 전체를 다시 처리합니다.

input이 4,789 토큰입니다. Haiku 4.5의 최소 캐시 가능 prefix가 4,096 토큰이므로, prefix 크기 조건은 이미 넘습니다. 마커를 붙이면 두 번째 호출부터 4,789 토큰이 캐시 읽기로 바뀝니다. adapters/usage.ts가 cache_read_input_tokens와 cache_creation_input_tokens를 이미 읽고 있어서 효과 측정은 별도 작업 없이 가능합니다.

두 가지를 같이 보시면 됩니다.

  • 렌더 순서가 tools → system → messages라, system 끝의 마커 하나가 tools + system을 함께 캐시합니다. 요청당 마커 상한은 4개입니다.
  • 대화가 길어지면 이력이 토큰의 대부분을 차지하는데, 고정 prefix 마커 하나로는 그쪽이 덮이지 않습니다. 가장 최근 턴의 마지막 블록에도 마커를 두면 이전 마커들이 읽기 지점으로 남아 캐시 적중이 증분으로 쌓입니다. 고정 prefix부터 시작해서 나중에 얹어도 됩니다.

3. pause_turn 은 서버사이드 툴을 붙이기 전에

지금은 툴을 전부 로컬에서 실행하므로 해당되지 않습니다. Anthropic native web_search 같은 서버사이드 툴을 붙이면 응답이 stop_reason: "pause_turn" 으로 끊깁니다.

현재 stopReason()은 이 값을 other로 떨어뜨리고, 에이전트가 오류로 보고 턴을 종료합니다. 동작하지 않는 것이 아니라 실패하는 형태입니다.

처리 방식은 user 메시지를 새로 붙이지 않고 히스토리를 그대로 재전송해 재개하는 것이고, 무한 일시정지를 막기 위해 재개 횟수에 상한을 둡니다. 지금 붙일 필요는 없고, 서버툴을 검토하실 때 확인하시면 됩니다.

4. 비대화형(원샷) 실행 경로

파이프로 프롬프트를 넣어 돌리려다 두 가지에 막혔습니다.

  • MCP 서버 기동(memory + playwright) 중에 도착한 첫 줄이 처리되지 않습니다. 세션 기록에는 뒤이어 들어간 /quit 만 남았습니다.
  • stdin이 닫히면 cli.ts의 terminal.question()이 ERR_USE_AFTER_CLOSE로 프로세스를 종료합니다.

실서버 검증을 tests/*-smoke.ts 로 따로 두신 이유도 여기 있어 보입니다. 프롬프트를 인자로 받아 한 턴만 돌고 끝나는 모드가 있으면 CI·스크립트·벤치마크에서 그대로 쓸 수 있고, 스모크마다 별도 드라이버를 두지 않아도 됩니다.

5. 테트리스를 텍스트로 돌릴 때

멀티모달 대신 보드를 데이터로 넘겨보라는 제안에 대해서입니다.

게임 테스트 플러그인이 Playwright MCP 프로세스 안의 컨트롤러로 게임 시계를 잡고 있으므로, 같은 자리에서 보드 상태를 직렬화해 꺼내면 화면 캡처 없이 텍스트가 됩니다. 시점 동기화도 컨트롤러가 쥐고 있어서 모델이 보는 보드와 실제 보드가 어긋날 여지가 적습니다. 새로 만드는 경로가 아니라 이미 있는 통로를 한 번 더 쓰는 쪽입니다.

매 조작 대신 "내릴 위치 + 회전"을 한 번에 받는 변형도 같은 이유로 붙이기 쉽습니다. 모델이 판단하는 동안 게임을 멈춰둘 수 있어 레이턴시가 결과에 섞이지 않습니다.

참고 — 측정 방법

재현하실 수 있게 적어둡니다. 둘 다 하네스의 createModelAdapter()를 그대로 써서 실제 실행과 같은 경로로 호출했습니다.

  • 캐싱 — 실제 내장 툴 정의를 실은 동일 요청을 Haiku로 연속 2회 전송. fetch를 감싸서 보낸 본문의 cache_control 등장 횟수와 받은 usage를 출력. 2회차 cache_read가 0이면 캐시가 만들어지지 않은 것으로 판정.
  • 스트리밍 — 스트리밍이 켜진 연결로 긴 답변을 요청하고, 응답을 clone() 해서 델타 도착 시각을 별도로 관측. 원본은 하네스에 그대로 넘겨 동작에 영향을 주지 않음. generate() 반환 시각과의 차이가 텍스트 도착과 화면 출력 사이의 간격.
