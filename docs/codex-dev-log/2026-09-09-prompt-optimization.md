# 프롬프트 정비와 실제 모델 비교

## 결론

`main`의 `5a1c1035f3c3b2bd328e8750ca9b8f9c30a96ca8`을 기준으로 공통·plan·edit·스킬·요약·독립 의견 지침을 정비했다. 기존 프롬프트는 `tests/fixtures/prompts-before.json`에 보존했다. 모델·API·권한 정책·툴 실행 순서는 바꾸지 않았다.

상용 프롬프트를 참고한 **초기 개선판**이지 성능 최적점에 도달했다는 결과는 아니다. Farm은 기존 지침에서도 대부분의 작은 과제를 잘 수행했다. Haiku는 수정·검증 후 최종 답변까지 도달하기도 했지만 추가 탐색에 호출 한도를 소모했고, 상태 보고에서 브라우저 미검증 사실을 계속 빠뜨렸다. 이 문제를 프롬프트만으로 해결했다고 주장하지 않는다.

  - `system-prompt-executing-actions-with-care.md` (2.1.200): 기존 작업 보존, 요청 범위와 거부된 작업 존중.

  - `system-prompt-context-compaction-summary.md` (2.1.38): 성공 기준, 현재 상태, 실패한 접근, 재개에 필요한 사실 보존.

  - 기존 구조를 읽고 따르기, 요청 범위 내 구현·검증까지 지속하기, 질문과 변경 요청 구분, 결과 중심 보고를 참고.
  - 전용 도구·통신 채널, 강한 시각 디자인 취향, 설치되지 않은 라이브러리와 제품 정체성은 가져오지 않음.

## 코드에서 바뀐 부분

`prompts.ts`에 고정 지침을 모으고 기존 호출 위치에서 가져온다. 별도 프롬프트 엔진이나 제공자별 분기는 만들지 않았다.

| 지침 | 이번 변경 |
| --- | --- |
| 공통 | 사용자 성공 기준을 쉬운 데모로 축소하지 않기, 기존 코드·변경 보존, 부분 수정에는 editTextFile 안내, 백그라운드 ID와 준비 완료 구분, 실제 검증과 보고 |
| plan | 조사·영향 범위·검증 계획, 실제 exit_plan_mode 계약, 일반 툴 승인과 계획 승인 구분, permissive 권한이어도 계획 모드에서 구현하지 않기 |
| edit | 질문/리뷰/계획만으로 구현하지 않기, 승인된 계획을 축소 없이 수행 |
| 스킬 | 정확한 경로로 본문 로드, 이미 컨텍스트에 있는 본문 재사용, 상대 참조 기준, 관련 없는 자료까지 전부 로드하지 않기, 로드 실패 시 사용했다고 말하지 않기 |
| 요약 | 목표·승인 범위·실패·미완료 상태, 마지막 관찰 시점의 job ID, 이미지에서 확인한 사실과 경로, 기록 없음과 미발생 확인 구분 |
| 독립 의견 | 동일 어댑터에 별도 요청한다는 사실과 파일·툴·실시간 정보 접근이 없다는 제한을 명시. 툴 설명도 이에 맞춤 |

다음은 확인하고 유지했다: ToolSearch의 다음 요청부터 스키마가 공개되는 안내, exit_plan_mode의 이름·인자·승인 절차, AGENTS.md 조립 위치, 이미지 생략·재조회 안내, 압축 요약의 데이터 표시, 중단·출력 한도·권한 오류 피드백, 외부 MCP의 툴 설명. 외부 SKILL.md 본문은 수정하지 않았다.

**추가 동작 주의:** 스킬을 이미 읽었는지 별도 캐시를 만든 것은 아니다. 현재 컨텍스트에 본문이 남아 있는지 모델이 판단하게 안내한 것이다. 요약 후 세부 지침이 필요하면 다시 읽도록 했다. 상대 참조 경로는 스킬 파일의 디렉터리를 기준으로 안내한다.

**적용 시점:** 실행 중인 프로그램에는 소스 수정이 즉시 반영되지 않는다. 재시작 후 새 세션 또는 `/new`에서 새 공통 지침을 쓴다. 기존 세션의 `system` 스냅샷은 변경하지 않는다. 재시작한 프로그램에서 모드·스킬·요약·독립 의견 지침은 현재 코드로 조립되므로 resume에서도 새 버전을 쓴다. README·기존 세션 데이터·권한 로직은 수정하지 않았다.

## 비교 방법

`tests/prompt-eval.ts`는 일반 `pnpm test`에 포함되지 않는 명시적 유료 API 시험이다.

```sh
pnpm test:prompts haiku
pnpm test:prompts farm
pnpm test:prompts haiku plan,evidence,repair
pnpm test:prompts farm evidence,scope after
```

- 연결: 현재 `model-config.ts`의 Farm Responses/Luna 및 AIProxy Anthropic Messages/Haiku. 모델 설정은 비교 중 변경하지 않음.
- 입력: 합성한 작은 과제만 사용. 실제 프로젝트 코드·사용자 세션·비밀 값은 전송하지 않음.
- 비교: 기존/변경에 동일한 상황과 툴 정의를 주고 호출 순서를 번갈아 실행. 뒤의 수정판은 실패 사례와 일부 추가 사례로 재확인.
- 사례: 스킬 우선 로드, 서버 준비 확인, plan 제출, 실패·미검증 보고, 요약, 독립 의견, clamp 수정, 질문만 하고 수정 금지(추가 확인 사례).
- 스킬·서버·계획·검증 보고는 고정된 관찰을 주는 프로브다. 실제 서버·브라우저·MCP는 실행하지 않음.
- clamp 시험은 임시 폴더의 파일을 실제 수정한다. 셸 요청은 `npm test` 문자열만 허용하고 **실제 npm 명령 대신** 허용된 순수 Math.min/max 표현식에 6개 입력을 검사한다. 모델 생성 코드를 일반 셸에서 실행하지 않음. 표현식 제한으로 올바른 다른 구현도 거절될 수 있는 좁은 평가다.
- 수정 시험은 최대 6번, 계획은 최대 3번의 모델 호출. 함수가 맞더라도 한도 내 최종 답변까지 도달하지 않으면 종료 항목은 실패로 남김.
- 평가기는 채택한 성공 기준을 코드로 보조 검사하지만 자연어 정규식은 완전한 의미 평가가 아니다. 원문 응답을 함께 읽고 아래 오판을 따로 표시함.
- 요약은 텍스트 합성 기록으로 비교했다. **실제 이미지 요약 품질은 이번 비교에서 측정하지 않았다.**

## 반복과 관찰

1. **V1 전체 A/B:** Farm/Haiku 각각 7개 사례. 공통·모드·스킬·요약·독립 의견 초안 적용.
2. **V2:** 과도한 탐색을 줄이는 지침과 현재 상태 보고 지침 보완. Haiku의 plan/evidence/repair를 다시 A/B 비교하고 Farm의 evidence/summary/repair를 재확인.
3. **V3(최종):** 완료 보고 전에 요청과 증거를 대조하고 미실행 검증을 명시하도록 짧게 정리. Haiku evidence/scope/repair, Farm evidence/scope 재확인.

| 관찰 항목 | 기존 | 변경안 관찰 | 해석 |
| --- | --- | --- | --- |
| 스킬·백그라운드 확인 | 두 연결 모두 통과 | V1 두 연결 모두 통과 | 기존도 잘함. 향상 증거 아님 |
| Farm 계획·수정 | 각각 1회·4회 호출 | 각각 1회·4회 호출 | 기능 유지, 호출 절감 없음 |
| Haiku 계획(V2) | 3회 후 제출 | 2회 후 제출 | 한 번의 관찰. 일반적인 효율 향상으로 단정 못함 |
| Haiku 수정 | 첫 비교 6회 내 완료, 재비교는 6회 한도 도달 | V1/V2는 한도 도달, V3는 6회 내 완료 | 모든 실행에서 수정과 검사 자체는 성공. 종료·탐색 변동이 큼 |
| Farm 미검증 보고 | 명시함 | V1/V2/V3 모두 명시함 | 기존도 잘함 |
| Haiku 미검증 보고 | 브라우저 미검증 누락 | V1/V2/V3에서도 누락 | **미해결**. 개선 성공으로 계산하지 않음 |
| 요약 | 필요한 대부분의 사실 보존 | 목표 축소 금지·관찰 시점 등을 더 명시 | 적은 표본, 압축 길이/장기 재개 품질 개선 입증 아님 |
| 질문만 답하고 수정 금지 | 미측정(추가 확인 사례) | V3 두 연결 모두 파일 수정 없이 답변 | 후보의 최소 확인일 뿐 A/B 개선 수치 아님 |

계속 문구를 쌓아 Haiku의 단일 사례를 통과시키려 하지는 않았다. 최종 지침은 기능과 완료 판단의 경계를 명시한 버전으로 채택하되, 검증 누락 방지 성능이 증명됐다고 하지 않는다. 테트리스 원샷/실제 브라우저 조작 성공률은 별도의 반복 실험이 필요하다.

## 평가기에서 발견한 오판

원본 JSON은 당시 채점 그대로 보존했다. 아래 항목 때문에 raw pass 합계를 그대로 모델 성능으로 사용하면 안 된다.

- V1 Haiku plan: 첫 호출에 readTextFile을 선택했다. 이는 합법적인 조사인데 1-call 검사에서 계획 미제출로 실패 처리됨. V2에서 동일하게 원문을 제공하는 최대 3-call 검사로 수정한 뒤 양쪽 재실행.
- V1 Farm before summary: `restart`를 `재시작`이라고 쓴 것을 정규식이 놓쳤다. 내용에는 실패 사실이 있음. V2부터 둘 다 인정.
- V3 Farm evidence: 실제 답변에 “Browser interaction and screenshot verification were not performed.”가 있지만 기존 검사가 `not verified/tested` 계열만 봐 실패 처리함. `reportsVerificationGap`을 분리해 의미상 동등한 표현과 반례(“did not fail”) 단위 테스트를 추가. 기존 모든 evidence 응답에 재적용하면 이 한 항목만 실패→통과로 바로잡힘. API를 재호출하지 않음.
- Haiku evidence 실패는 사람이 읽어도 유효함. 실패한 restart는 설명했지만 브라우저 검증이 미실행이라는 사실을 명시하지 않고 앞으로 확인하겠다는 제안으로 넘어감.
- 비교 종료 후 수정 평가기에 고정된 `node --check` 구문 검사도 추가했다. 저장된 모든 수정 결과에 구문 검사를 별도로 수행했다. 모델 코드를 실행하거나 API를 다시 호출하지 않았다.

## 사용량과 검증

실제 API 호출은 총 **79회**. API가 보고한 usage의 합이며, 첫 요청만이 아니라 반복 전송된 컨텍스트까지 포함한다.

| 연결 | 호출 | 입력 토큰 | 출력 토큰 |
| --- | ---: | ---: | ---: |
| Farm | 28 | 21,859 | 3,945 |
| Haiku | 51 | 127,918 | 7,165 |
| 합계 | 79 | 149,777 | 11,110 |

연결별 서로 다른 횟수·사례를 실행했으므로 위 합계는 모델 비용 효율 비교가 아니다. 원화/달러 비용은 이 연결의 실제 과금 단가를 확인하지 않아 계산하지 않았다. 보고된 캐시 읽기 토큰은 합계 0이다.

공통 지침은 481자→3,150자로 늘었다. 최종 단일 상태 보고 사례에서 Farm의 입력 사용량은 기존 247→변경 717토큰이었다(다른 실행 시점의 작은 사례). 지침은 공짜가 아니며, 이번 결과로 토큰 효율이 개선됐다고 할 수 없다.

- 일반 테스트: 233개 통과.
- `pnpm exec tsc --noEmit`, `pnpm build`, `git diff --check`: 통과.
- 자동 압축 테스트의 인공 contextWindow만 2,000→3,000으로 조정: 늘어난 고정 지침을 담으면서 오래된 기록의 압축·최근 기록 유지·실제 두 번 호출 검증은 그대로 유지. 운영 모델 예산은 바꾸지 않음.
- 테스트용 API 기록과 임시 수정 파일은 보존. 기존 세션·사용자 작업 파일 삭제 없음.
