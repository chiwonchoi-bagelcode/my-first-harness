# Anthropic 프롬프트 캐시 (cache_control)

작성일: 2026-09-10

배경: 시니어 피드백 4번 "anthropic 캐싱 붙이기". 서버가 접두어(tools → system → messages 순서로 렌더링된 바이트)의 계산 상태를 저장해 두고, 다음 요청의 접두어가 브레이크포인트까지 바이트 단위로 같으면 재사용한다. 읽기는 기본 입력가의 0.1배, 쓰기는 1.25배(5분 TTL, 읽힐 때마다 갱신). Haiku 4.5는 접두어가 4,096토큰 이상일 때만 캐시되고 짧으면 표시가 조용히 무시된다. 브레이크포인트는 요청당 최대 4개. 근거: Anthropic 프롬프트 캐싱 문서(claude-api 스킬의 `shared/prompt-caching.md`).

## 시작 전 상태 (세션 기록 집계)

코드에는 캐시 제어가 없었고 응답 usage의 캐시 필드를 JSONL에 기록하는 매핑(`adapters/usage.ts`)만 있었다. 전체 세션 JSONL의 `model-response.usage`를 제공자별로 합산했다.

| 연결 | 호출 | 입력 토큰 | 캐시 읽기 | 읽기 비율 |
| --- | ---: | ---: | ---: | ---: |
| bakery-farm (Responses) | 264 | 6,167,241 | 4,231,040 | 69%, 181회 적중 |
| bagel-openai (Responses) | 1 | 5,304 | 0 (쓰기 5,301) | 표본 부족 |
| bagel-anthropic (Messages) | 113 | 2,974,140 | 0 | 0% |

Farm은 OpenAI 쪽 자동 접두어 캐싱으로 코드 없이 잡히고 있었다. Anthropic은 명시적 표시가 필요해 113회 모두 0이었다.

Haiku 세션 10개·113요청의 실제 전송 본문으로 "직전 요청과 바이트가 같은 접두어" 비율을 재면 87%였다(문자 수 기준 추정). tools+system은 요청당 약 25,000자(전체의 8%)로 최소치를 넘는다. tools가 바뀐 요청 4회(ToolSearch로 MCP 정의 공개), system이 바뀐 요청 4회(모드 전환·스킬 재로딩).

## 설계

두 개의 스위치를 둔다.

- 연결 설정 `promptCache?: boolean`(`adapters/anthropic-messages.ts` Config, `model-config.ts`의 haiku에서 켬): 이 제공자가 명시적 표시를 요구하고 우리가 쓰겠다는 뜻. `stream`과 같은 위치.
- 요청 표시 `LLMRequest.promptCache?: boolean`: "이 접두어를 다음 요청에서 다시 보낼 예정"이라는 호출 패턴 정보다. 코어의 `step()`만 켠다. 요약(compaction)과 다른 LLM에게 묻기(other-llm)는 한 번만 보내는 요청이라 표시하면 쓰기 요금만 내고 읽히지 않으므로 켜지 않는다. 설명 단계에서는 연결 설정 하나만 이야기했는데, 구현 중 압축 요약 요청(큰 대화 JSON을 한 번만 보냄)이 최상위 자동 표시 때문에 1.25배를 낼 문제를 발견해 요청 표시를 추가했다.

둘이 모두 참일 때 어댑터가 본문에 붙이는 것은 둘이다.

- `system`을 문자열에서 블록 배열로 바꾸고 마지막(유일한) 블록에 `cache_control: { type: "ephemeral" }`. tools가 system 앞에 렌더링되므로 툴 정의와 지침이 한 덩어리로 캐시된다.
- 본문 최상위 `cache_control: { type: "ephemeral" }`. 서버가 messages의 마지막 캐시 가능 블록에 표시를 찍고 대화가 늘면 따라간다. 이전 스텝의 자리는 읽기 지점으로 남는다. 참조 문서가 에이전트 루프에 권하는 "system 명시 표시 + 최상위 자동 표시" 조합이다.

표시는 전송 시점에만 붙고 세션·replayState·JSONL의 message에는 남지 않는다(`withImagePaths`와 같은 성질). `toMessages`의 변환, 응답 처리, 세션 형식은 바뀌지 않았다. Responses 어댑터는 요청 표시를 무시한다. TTL은 기본 5분이다. 스텝 간격이 초 단위라 읽힐 때마다 갱신되고, 사용자가 5분 넘게 생각하면 다음 턴 첫 요청은 콜드 미스다.

우리 하네스에서 접두어를 깨는 것: ToolSearch로 툴 정의가 늘 때, plan/edit 전환이나 스킬 재로딩으로 system이 바뀔 때, 압축·긴 툴 결과 자르기로 messages 앞부분이 바뀔 때, 이미지 예산 초과로 오래된 이미지가 텍스트 안내로 바뀔 때. 각각 그 뒤 첫 요청이 전체를 다시 쓴다. Haiku에는 대화 중간 system 메시지가 없어(Opus 5 계열만) 모드 지침이 system에 있는 현재 구조는 그대로 둔다.

## 검증

모의(`tests/prompt-cache.test.ts` 5개 신규): 두 스위치가 모두 참일 때 system 블록 배열과 최상위 표시, 툴·메시지·replayState에는 표시 없음, usage 매핑; 하나라도 없으면 예전 본문; 빈 system은 빈 블록을 만들지 않음; Responses 어댑터는 표시 무시; haiku 연결이 켜져 있고 코어가 스텝에는 `true`, 요약에는 `undefined`를 넘김. `pnpm test` 272개, `pnpm exec tsc --noEmit`, `git diff --check` 통과.

실제 API(유료, `pnpm test:anthropic` 4요청): AIProxy가 `cache_control`을 통과시키고 캐시 필드를 돌려준다. 스모크의 tools 13개(약 3,300자)와 짧은 지침은 4,096토큰에 못 미쳐 고정 지침 본문 200줄을 system에 덧붙였다(실제 앱의 접두어 약 25,000자와 비슷한 크기). 요청 2는 툴 정의를 하나 추가하므로 접두어가 바뀐다.

| 요청 | 전체 입력 | 캐시 읽기 | 캐시 쓰기 | 정가 처리 |
| --- | ---: | ---: | ---: | ---: |
| 1 텍스트 | 9,989 | 0 | 9,986 | 3 |
| 2 툴 호출 (tools 변경) | 10,080 | 0 | 10,077 | 3 |
| 3 툴 결과 → 답 | 10,173 | 10,077 | 90 | 6 |
| 4 다음 턴 | 10,240 | 10,167 | 70 | 3 |

요청 3·4가 문서의 "정상 루프 신호"와 일치한다: 읽기는 직전 접두어 전체이고 스텝마다 커지며, 쓰기는 새로 붙은 꼬리만, 정가 처리는 몇 토큰. 요청 3 기준 요금은 10,077×0.1 + 90×1.25 + 6 ≈ 1,127토큰 상당으로, 캐시 없이 10,173을 내는 것과 비교해 약 89% 감소다. 세션 전체로는 앞의 87% 추정을 적용하면 입력 비용이 대략 4분의 1로 내려간다. 첫 토큰 지연은 이번에 측정하지 않았다.

집계 방법이 그대로 쓰이므로 앞으로 JSONL의 `cachedInputTokens` 합계가 0이면 접두어를 깨는 변경이 들어간 것이다. 스모크의 단정(첫 요청 쓰기 > 0, 3번째 읽기 > 0, 4번째 읽기 ≥ 3번째)이 상시 검사다.

## 남긴 것

- Farm·AIProxy Luna는 손대지 않았다. OpenAI 쪽은 자동이다.
- 툴을 많이 꺼서 tools+system이 4,096토큰 아래로 내려가면 system 표시는 무시되고 대화가 그 크기를 넘은 뒤부터 최상위 표시만 동작한다.
- 요약 호출은 system·tools가 달라 스텝의 캐시를 공유하지 못한다. 압축당 한 번이라 두었다.
- 1시간 TTL, 사전 예열(`max_tokens: 0`), 캐시 진단 헤더는 쓰지 않았다.
