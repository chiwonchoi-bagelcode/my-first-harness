# Game Testing 플러그인 설계 계획

작성일: 2026-09-09

상태: 설계 초안. 실행 코드는 아직 구현하지 않았다. 메인 저장소와 기존 워크트리는 수정하지 않았다.

## 1. 도입 동기

최종 과제는 하네스가 게임을 만들고, 브라우저에서 직접 플레이하며 문제를 발견하고 수정하는 것이다.

현재 하네스에는 Playwright MCP의 페이지 탐색·키 입력·화면 캡처 도구가 연결되어 있다. MCP가 반환한 이미지는 공통 이미지 블록으로 변환되어 다음 모델 요청에 들어간다. 그러나 모델이 화면을 해석하고 다음 입력을 결정하는 동안에도 게임은 계속 진행된다. 화면이 오래되어 잘못된 시점에 입력하거나, 입력하기도 전에 게임이 끝날 수 있다.

이번에는 새 게임 전용 모델을 설치하지 않는다. 기존 모델과 Playwright MCP를 유지하고, 게임이 실제로 시간을 제어할 수 있는 구조인지 검증한 뒤 느린 속도로 플레이하는 기능을 만든다.

학습할 핵심은 다음 세 가지다.

- 모델이 결정하는 작업 절차와, 코드가 보장하는 실행 동작을 분리한다.
- 모델의 관찰→입력 지연과 게임 시간의 관계를 측정한다.
- 성공 기준과 한계를 명시하고, 감속 플레이 성공을 정상 속도의 QA 성공으로 과장하지 않는다.

## 2. 목표와 비목표

### 목표

1. 스킬과 툴을 `game-testing`이라는 하나의 기능 단위로 제공한다.
2. 기존 Playwright MCP가 사용하는 게임 탭을 그대로 제어한다.
3. Clock 적용 가능성을 실제 관찰로 검증한다.
4. 모델 응답을 기다리는 동안에도 게임이 설정된 느린 속도로 진행하게 한다.
5. 캡처에서 실제 입력까지 지연과 실제 게임 시간 진행량을 기록한다.
6. 검증된 이미지와 관찰 기록을 근거로 플레이·QA 결과를 보고한다.
7. 기능을 종료하거나 끄면 감속 작업과 누른 키를 정리한다.

### 비목표

- 모든 웹 게임을 반드시 멈추는 범용 기능.
- 게임 내부 상태를 바꿔 성공을 만들거나 블록 배치를 직접 조작하는 기능.
- 인간과 동일한 인지·판단·입력 특성을 재현한다는 주장.
- 정상 속도의 성능, 오디오, 네트워크 동기화까지 감속 테스트로 검증.
- 이번 단계에서 새 모델 설치, 학습, provider 변경, 별도 브라우저 자동 생성.

## 4. 시간 제어의 원리와 제한

Playwright Clock은 페이지의 Date, performance, setTimeout, setInterval, requestAnimationFrame 등 시간 관련 API를 제어 가능한 구현으로 바꾼다. JavaScript 실행 전체, 서버 시간, 모든 외부 이벤트를 정지시키는 기능이 아니다.

- 게임이 해당 API를 통해 진행한다면 정지·수동 진행이 적용될 수 있다.
- 네트워크 메시지, Worker의 계산, 미디어 재생 등은 페이지 Clock만으로 제어된다고 가정하지 않는다.
- 키 이벤트가 직접 상태를 바꾸는 게임은 시계 정지 중에도 입력에 반응할 수 있다.
- Clock은 게임 코드가 타이머를 사용하기 전에 설치한다. 기존 페이지에서 뒤늦게 적용하는 대신 모델이 재시작 필요성을 설명하고 통제된 재로드로 시작한다.
- 설치 성공과 게임 진행 제어 성공은 별개다.
- Clock에는 임의의 배속을 설정하는 setSpeed API가 없다. 감속은 별도의 진행 루프로 구현해야 한다.
- runFor는 지정 시간의 타이머·프레임을 진행한다. 게임 프레임을 생략할 수 있는 fastForward를 플레이용 대체재로 사용하지 않는다.

공식 근거:

- https://playwright.dev/docs/clock
- https://playwright.dev/docs/api/class-clock

## 6. 스킬과 툴의 책임

### 스킬: 언제, 왜, 어떤 순서로 검사하는가

스킬 목록에는 이름·설명·위치만 노출한다. 모델이 선택하면 SKILL.md 본문을 읽는다. 본문 전체를 매번 시스템 프롬프트에 넣지 않는다.

스킬 내용은 다음 절차를 포함한다.

1. 테스트 대상 URL, 요구사항, 성공 기준을 확인한다.
2. 게임 재시작과 시간 제어가 허용되는 범위인지 확인한다.
3. 게임 탭을 고정하고 Clock을 설치한다.
4. 정지 중 상태 유지, 수동 진행 시 상태 변화, 키 입력과 캡처를 확인한다.
5. 고정 배속으로 관찰→입력 루프가 작동하는지 먼저 시험한다.
6. 여러 지연 표본을 모아 목표 반응 지연에 맞는 배속 후보를 정한다.
7. 감속 상태에서 화면을 보고 실제 키 입력으로 플레이한다.
8. 예상 결과와 실제 결과를 비교하고 실패 장면과 재현 절차를 기록한다.
9. 종료하고, 가능하면 정상 속도에서 기본 동작을 별도로 확인한다.

Clock 함수가 성공했다는 이유로 적용 가능 판정을 내리지 않는다. 화면이 우연히 정지해 있는 메뉴에서 한 번 캡처한 결과도 증거로 충분하지 않다. 움직이는 게임 장면에서 여러 번 확인한다. 실패하면 내부 상태를 조작해 테스트를 통과시키지 말고 부적합 또는 미확인으로 보고한다.

### 툴: 실행과 계측을 보장한다

초안에서는 작은 역할의 툴 5개를 사용한다. 인자 규격과 반환 형식은 구현 전 다시 검토한다.

| 툴 | 핵심 입력 | 핵심 결과 |
| --- | --- | --- |
| gameTestStart | 대상 탭, 초기화할 URL | testId, 고정 탭 정보, Clock 설치 상태 |
| gameTestClock | testId, 동작(pause/advance/rate/resume), 필요 시 ms/rate | 모드, 요청 배속, 누적 가상 시간, 지연 |
| gameTestObserve | testId | 기존 이미지 형식의 스크린샷, observationId, 시간 정보 |
| gameTestAct | testId, observationId, keys, holdGameMs | 입력 적용 시각, 지연 표본, 누적 시간 |
| gameTestStop | testId | 진행 루프·키·시간 복구 결과, 계측 요약 |

캡처와 입력을 신규 엔진으로 구현하지 않는다. 기존 MCP/Playwright 기능을 감싼다. Observe와 Act를 감싸는 이유는 화면과 입력의 인과관계를 ID로 연결하고 실제 시각을 기록하기 위해서다. 기존 일반 브라우저 툴로 조작한 구간은 자동으로 유효한 지연 표본으로 취급하지 않는다.

gameTestAct는 모델이 정한 입력만 수행하며 게임 전략을 내장하지 않는다. 특정 키를 눌러야 성공하는 루틴을 코드에 강제하지 않는다.

## 7. 같은 브라우저에 연결하는 방식

설치된 Playwright의 `browser_run_code_unsafe` 구현은 전달한 함수에 현재 탭의 `page`를 넘긴다. 따라서 동일 MCP 연결에서 page.clock을 호출할 수 있다는 것은 코드로 확인했다.

다만 다음 두 사실도 확인했다.

- 해당 툴은 전달된 비동기 함수가 끝나기를 기다린다.
- 호출마다 VM 컨텍스트를 새로 만든다. 호출 간 전역 변수나 타이머가 안전하게 유지된다고 가정하지 않는다.

### 우선 검증할 구현안: 하네스 측 진행 루프

기존 연결을 노출하는 작은 내부 bridge를 둔다. 모델에게 MCP Client 자체를 주지는 않는다. 플러그인은 bridge를 통해 유한한 Clock 명령을 보낸다.

```text
game-testing controller
  → 기존 Playwright MCP Client
  → browser_run_code_unsafe
  → 선택한 게임 탭의 page.clock
```

시간 진행 스케줄러는 하네스 프로세스에 두고, 짧고 끝나는 runFor 요청을 반복한다. 모델 요청이 진행 중이어도 스케줄러는 동작한다. 영원히 끝나지 않는 MCP 호출을 만들지 않는다.

탭을 단순히 현재 선택 탭으로 취급하지 않는다. 테스트 시작 시 실제 페이지 객체를 재식별할 수 있는 방법과 수명을 검증하고 고정한다. URL만으로 고정하면 같은 URL의 여러 탭을 구분할 수 없다. MCP 재연결·탭 닫힘·예상하지 않은 이동은 연결 손실로 처리한다.

현재 MCP 호출/페이지 작업의 직렬화 특성, 호출 비용, 탭 고정 방식은 실제 검증 전이다. 같은 페이지에 대한 시간 진행과 캡처·입력은 짧은 작업 큐로 조율하되 모델 추론은 이 큐에 넣지 않는다. 일반 MCP 호출이 탭을 바꾸거나 장시간 대기하는 경우도 검증한다.

이 방식이 너무 느리거나 페이지 작업과 충돌하면 무리하게 우회하지 않는다. 같은 브라우저를 소유하는 MCP 측에 작은 지속 실행 컨트롤러를 추가하는 대안을 설명하고 승인받는다. 별도 MCP/브라우저를 몰래 새로 띄우거나 공유 전역 객체에 타이머를 숨기는 방식을 기본 설계로 삼지 않는다.

## 8. 감속 루프

가상 시계는 일시정지 상태에서 시작한다. 단조 증가하는 현실 시계를 사용해 다음 목표를 계산한다.

```text
목표 가상 경과 시간 = 현실 경과 시간 × rate
진행할 시간 = 목표 가상 경과 시간 - 이미 진행한 가상 시간
```

그 차이를 작은 구간으로 나누어 runFor로 진행한다. runFor 호출은 중첩하지 않는다. 호출 자체의 소요 시간도 현실 경과 시간에 포함한다.

이 방식은 연속 배속의 근사다. 내부적으로는 작은 시간 단위로 진행한다. 요청 간격이 너무 크면 움직임이 뭉치고, 너무 작으면 MCP 호출 비용이 커진다. 따라서 간격은 실제 측정 후 결정한다.

요청 배속을 따라가지 못하면 실제 달성 배속과 backlog를 기록한다. 긴 정체 후 한꺼번에 시간을 진행해 게임이 갑자기 도약하게 하지 않는다. 임계치를 넘으면 테스트를 중단/일시정지하고 원인을 알린다. 이때 인간 유사 지연 실험이 유효하다고 보고하지 않는다.

키를 놓는 시점도 게임 시간으로 관리한다. 모델이 다음 응답에서 key-up을 보내야 하는 구조는 피한다. 실패나 종료에서는 눌린 키를 해제한다.

## 9. 지연 측정과 배속 계산

관찰 하나와 그 관찰을 근거로 한 입력 하나를 observationId로 연결한다.

- 캡처 시작·완료: 실제 화면 획득 시각은 이 구간에 있으므로 범위를 기록한다.
- 하네스가 이미지 결과를 받은 시각.
- 모델 요청 시작·완료: 기존 로그를 활용하고 필요하면 최소한의 상관 ID만 추가한다.
- 입력 명령 전송·완료 시각.
- 관찰과 입력 시점의 가상 게임 시간.

서로 다른 프로세스의 performance.now 값을 직접 빼지 않는다. 우선 하네스의 단조 시계로 공통 구간을 기록하고, 브라우저 측 시간은 별도 가상 시간으로 보관한다. 정확한 이벤트 적용 시각을 계측하지 못하면 입력 완료 시각을 대용으로 썼음을 명시한다. 측정용 페이지에서는 실제 keydown 수신 시각으로 오차를 검증한다.

계산 예시는 다음과 같다.

```text
대표 관찰→입력 지연 L = 4초
사용자가 정한 목표 지연 H = 게임 시간 0.25초
배속 후보 r = H / L = 0.0625
```

0.25초는 보편적인 인간 반응속도가 아닌 예시다. 실험 목표로 선택한 값을 기록한다. 첫 단계에서는 충분한 여러 표본을 수집하고 중앙값, 느린 표본, 범위 등을 함께 보고한다. 캡처·입력 도구만 호출한 왕복 시간으로 모델 판단 시간을 대신하지 않는다.

배속 후보를 정한 뒤 해당 배속에서 다시 검증한다. 배속은 한 플레이 구간에서 고정하며 매 응답마다 자동 변경하지 않는다. 긴 추론과 추가 도구 호출은 여전히 긴 반응을 만들 수 있다. 다른 작업/모델로 바뀌면 측정을 다시 한다.

인간과 비슷하게 만드는 것은 관찰에서 입력까지의 게임 시간 차이뿐이다. 지속적인 시각 관찰, 행동 예측, 숙련도, 입력 빈도까지 동일하게 만든 것은 아니다.

## 10. 스킬·툴 소유권과 수명

HarnessPlugin에 선택적인 스킬 메타데이터/파일 자산 선언을 추가하는 최소 확장을 제안한다. 기존 setup(tools) 호출부를 전부 바꾸는 대신 플러그인 메타데이터에서 스킬 소유권을 연결한다.

- 플러그인 활성화: 툴과 스킬 메타데이터를 노출한다.
- 개별 스킬 비활성화: 스킬 목록에서 제외하되 툴을 자동으로 끄지는 않는다.
- 플러그인 비활성화: 새 호출을 차단하고 테스트 정리 후 툴·스킬 노출을 해제한다.
- 스킬 재검색: 파일 스킬과 플러그인 소유 스킬을 합성한다. replace로 플러그인 스킬을 지우지 않는다.
- 중복 이름: 이 단계에서는 묵시적으로 덮어쓰지 않고 충돌을 알린다.
- 과거 대화에 이미 읽힌 스킬 본문을 삭제하지 않는다. 비활성화는 향후 노출과 실행 가능성을 제어한다.

MCP를 끄거나 다시 연결하기 전에는 의존하는 게임 테스트를 먼저 정리한다. 사용자가 브라우저를 닫았거나 연결이 끊겨 복구 호출을 할 수 없다면 실패 사실을 남긴다. Clock.resume은 제어된 시계의 진행 재개이지 원래 네이티브 API의 완전 복원은 아니다. 완전한 초기화가 필요하면 사용자에게 재로드 필요성을 알린다.

프로세스 강제 종료 후까지 복구를 보장하지 않는다. 기존 브라우저 탭을 자동으로 닫거나 새로고침해 상태를 없애지 않는다.

## 11. 구현 단계와 통과 조건

### 단계 0 — 연결·감속 가능성 검증

하네스의 실제 게임을 바로 수정하지 않고, 로컬 임시 페이지로 검증한다.

- MCP가 가진 동일 페이지에 Clock 설치 가능.
- 정지 중 타이머 기반 상태가 유지되고 runFor 때만 변화.
- 키 입력, canvas 렌더, 이미지 반환이 함께 작동.
- 짧은 runFor 요청을 반복하면서 모델 호출을 흉내 낸 대기 중에도 시간이 진행.
- 탭이 여러 개여도 게임 탭을 잘못 조작하지 않음.
- 스크린샷 대기나 MCP 작업 큐로 감속 루프가 장기간 막히지 않음.

이 단계가 실패하면 이후 플러그인 통합을 진행하지 않고 대안을 재설계한다.

### 단계 1 — 고정 배속 플러그인

5개 툴의 최소 실행 경로, 고정 배속 controller, SKILL.md, 소유권과 cleanup을 구현한다. 자동 배속 산정은 아직 넣지 않는다.

통과 조건: 사용자가 정한 느린 배속에서 실제 모델이 화면→키 입력 루프를 수행하고, 기다리는 동안 게임이 계속 천천히 진행함을 로그로 확인한다.

### 단계 2 — 지연 계측과 배속 제안

관찰/입력 ID, 지연 표본과 측정 오차, 배속 후보 및 달성 배속 보고를 추가한다. 계산은 코드가 수행하고 적용 여부는 스킬 지침에 따라 모델이 결정한다.

### 단계 3 — 실제 테트리스 QA

미리 정한 요구사항을 기준으로 시작·이동·회전·낙하·줄 제거·게임 오버·재시작 등을 검증한다. 게임 내부 상태를 읽어야 하는 진단은 시각 플레이와 구분해 보고한다. 감속 테스트 후 정상 속도 smoke test를 별도로 수행한다.

## 12. 검증 목록

- 모의 단조 시계로 rate 계산과 runFor 비중첩 검증.
- MCP 지연이 커졌을 때 backlog와 실제 배속 보고 검증.
- 툴 실패·탭 닫힘·MCP 종료·플러그인 토글 시 cleanup 검증.
- 스킬 재검색·개별 비활성화·소유 플러그인 해제 조합 검증.
- PNG 결과가 기존 이미지 경로를 통해 모델에 도달하는지 검증.
- 일반 페이지 타이머와 서버 주도 상태 등 적용 가능/불가능 사례를 각각 검증.
- 실제 모델을 사용하는 검증은 API 비용 발생을 명시하고 별도로 실행.
- 정상 속도에서의 문제를 감속 성공으로 은폐하지 않는 보고서 확인.

## 13. 이번 설계에서 명시적으로 추가한 정책

다음 항목은 사용자와 합의한 큰 방향을 구현하기 위해 제안한 세부 정책이며, 이미 구현된 기능이 아니다.

- 초기에는 동시에 하나의 게임 테스트만 허용한다.
- 첫 실험은 고정 배속, 자동 비율 산정은 후속 단계로 나눈다.
- 탭 고정, 관찰 ID, 누른 키 자동 해제, backlog 초과 시 중단을 둔다.
- 플러그인 스킬 이름 충돌은 자동 덮어쓰기하지 않는다.
- 임의 게임의 현재 진행 상태를 보존한 채 Clock을 설치할 수 있다고 약속하지 않는다.
- 원래 설정을 완전히 복원하지 못했거나 실제 배속을 달성하지 못하면 성공으로 보고하지 않는다.
