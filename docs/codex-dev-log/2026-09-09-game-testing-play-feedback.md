# Game Testing — 실제 플레이 세션 분석과 두 가지 수정

작성일: 2026-09-09

대상 세션: `c90b42a6-1134-40be-a392-c5e5b67ee145.jsonl` (17:20~17:43, Farm Luna, 5턴, 모델 호출 146회). 턴 2는 테트리스 제작, 턴 3·5는 사용자가 game-testing 스킬로 시킨 QA 플레이. 사용자 소감: "뭔갈 하긴 하는데 게임 플레이는 참 못하고, 그래도 되기는 한다. 이미지 호출로 토큰 비용이 너무 나가는 것 아닌가."

## 관찰

파이프라인은 두 턴 모두 지켰다: `readTextFile(SKILL.md)` → navigate → `Start(0.1)` → `check`(controllable) → 측정 Act → `rate` 1회(L 7,232ms → 0.035, L 4,228ms → 0.059) → 루프 → `Stop`. 금지 툴 0회. 턴 3 보고는 통과·미확인을 분리했고 "r/R/Enter 재시작 안 됨, 버튼 클릭은 규칙상 미시도"라는 발견을 남겼다.

플레이가 나쁜 이유(로그 근거):

- 판단 하나에 키 하나. Observe→Act 쌍으로만 움직여 셀 한 칸 이동에 모델 호출 2회(현실 약 7초). 조각 하나에 필요한 "이동 n회 → 회전 → 낙하"를 한 번에 표현할 툴이 없었다.
- 하드 드롭 반사. Space가 턴 3 21회 중 11회, 턴 5 25회 중 9회. 정렬 전에 떨어뜨려 쌓였다. 스크린샷에서 열을 정확히 읽지 못하는 것도 원인.
- 키 유지가 헛돌았다. 턴 5에서 200~400ms 유지(각 현실 3~7초)를 시도했다가 단타로 돌아갔다. 모델이 만든 게임에 키 반복이 없어 유지해도 한 칸만 움직인 것으로 보인다.
- 컴팩션이 플레이 중간에 끼었다. 관찰→입력 지연이 보통 3~6초인데 32.9초·46.1초·25.3초인 스텝이 셋 있고 각각 게임 시간 1,150·2,720·1,490ms가 통제 없이 흘렀다. 위치가 컨텍스트 압축 시점(턴 3 s22, 턴 5 s10·s43)과 일치한다.

토큰:

| 항목 | 값 |
| --- | --- |
| 총 입력 / 캐시 히트 | 4,202,351 / 3,204,608 (76%) |
| 총 출력 | 25,880 |
| QA 두 턴 입력 | 2.76M (108회) |
| 스크린샷 1장 (390×844 PNG 28KB) | 약 450~600 토큰 (입력 증분으로 역산) |
| 요청당 이미지 | 최대 20장, 요청 본문 최대 0.8MB |

이미지는 피크 스텝에서 약 34%, QA 턴 평균 약 28%였다. 더 큰 두 가지: (1) 턴 2의 `writeTextFile` 인자(테트리스 소스 전체)가 턴 3 첫 21스텝의 기본 입력 49~55k를 만들어 약 1.05M(세션의 1/4)을 차지했다(캐시 히트는 높았다). (2) 컴팩션이 실제 26~46k에서 발동했다. 임계값 128k인데, 추정기가 이미지 1장을 4,000토큰으로 잡아(실측의 7배) 과대 추정했기 때문이다. 요약 호출 3회 + QA 기억 상실 + 위의 게임 시간 점프.

부수: 세션 JSONL이 172MB. `model-request` 원문에 base64 이미지가 146번 중복 저장된다(미수정). 컨트롤러 스크린샷 `scale: "css"` 미지정도 남아 있다(이번엔 배율 1).

## 사용자 결정

제안 넷 중 1(이미지 토큰 추정 정정)과 3(입력 시퀀스)만 진행. 2(최근 N장만 이미지로 유지)와 4(플레이 전략 지침 강화)는 보류.

## 수정 1 — 이미지 토큰 추정

`token-budget.ts`에 `estimateImageTokens(width, height)`: `requestImageSize`로 구한 실제 전송 크기의 가로×세로 / 750, 최소 256. Anthropic의 공개 규칙이며 Farm 실측(390×844 ≈ 500)과 같은 자릿수다. `estimateMessageTokens`가 이 값을 쓰고, `context-manager.ts`의 `contextSize`(표시용 글자 수)는 토큰당 4자로 환산해 더한다. 값: 128×128 → 256, 390×844 → 439, 1280×720 → 1,229, 3456×2234 → 축소 전송 크기 1372×887 기준 1,623. 이 세션의 피크(20장)는 이전 80k에서 약 9k 추정으로 내려가 컴팩션이 발동하지 않았을 것이다.

## 수정 3 — `gameTestAct` 입력 시퀀스

- 인자 `inputs: [{ keys, holdGameMs, gapGameMs? }, …]`(1~16개)로 바꿨다. 단일 `keys/holdGameMs`는 제거. 각 입력은 keys를 동시에 누르고 `holdGameMs` 뒤 스케줄러가 놓은 다음 `gapGameMs`(게임 시간)를 기다려 다음 입력으로 넘어간다. 간격 대기는 `test-run.ts`의 게임 시간 타이머(`waitGameTime`)로 구현했고 키 해제와 같은 루프 훅에서 풀린다. 컨트롤러 오류·종료 시 타이머도 함께 거부한다.
- 결과: `inputs[].{keys, holdGameMs, pressedAtGameMs, releasedAtGameMs}`, 전체 `pressedAtGameMs`(첫 입력)·`releasedAtGameMs`(마지막)·`realMs`, `observationId`를 준 경우 첫 입력 기준 `observationToInputMs`·`observationToInputGameMs`.
- 같은 입력 안의 중복 키는 거부(반복은 별도 항목으로). 시퀀스 도중 테스트가 stopped/lost가 되면 실행한 개수를 오류에 남긴다. paused는 대기한다.
- 스킬 Phase 5: "관찰 한 번에 조각·상황에 필요한 전부(이동 → 회전 → 확정 입력 마지막)를 정해 하나의 `inputs`로 보낸다. 키 하나에 호출 하나는 느리고 비싸다. 긴 유지로 여러 칸을 움직이려면 이 게임이 키 반복을 지원하는지 한 번 확인하라"로 바꿨다. Phase 3의 측정은 한 개짜리 시퀀스.
