# MCP 서버 연결·툴 등록·실행

## 범위와 구조

사용자 승인 범위: 시작할 때 여러 MCP 서버를 연결하고, 서버의 툴을 기존 ToolManager에 등록해 기존 turn 루프로 실행한다. 실행 중 서버 on/off는 구현하지 않는다.

- `mcp-servers.ts`: 서버별 설정. stdio 두 개, Streamable HTTP 두 개.
- `mcp-client.ts`: 서버마다 Client/Transport 생성 → initialize → tools/list 전체 페이지 → 실행 함수를 붙여 등록. 실행 시 tools/call 요청.
- 공개 툴 이름은 `mcp__서버이름__원래툴이름`. 원래 이름은 closure에 보존한다. 긴 이름/특수문자는 해시를 붙여 API의 64자 제한에 맞춘다.
- 연결은 병렬로 하지만 등록 순서는 설정 순서로 고정한다.
- 한 서버 연결 실패는 안내하고 건너뛴다. MCP 요청 제한 시간은 15초다. 무거운 툴에는 향후 별도 설정이 필요하다.
- 기존 ToolManager가 JSON 인자 파싱/검증/실행 오류 처리를 맡고, turn이 MCP 결과도 동일하게 history/messages에 기록한다.
- 서버의 `isError` 결과는 실행 오류로 전달한다. 텍스트와 structuredContent는 문자열로 전달하고, 이미지/오디오/바이너리는 현재 지원하지 않는다고 표시한다.
- `/quit`, 정상 루프 종료, 루프 예외 시 연결을 닫는다. 대화 입력 중 Ctrl+C에서도 stdio 자식 프로세스를 정리한다. 서버별 런타임 끄기/재연결/목록 변경 구독은 아직 없다.

## 참고한 실제 구현

로컬 DSH `packages/mcp/mcp-client/src/transport.ts`, `connection.ts`, `tools.ts`를 확인했다. 서버별 Client/Transport, 목록 조회, 서버 이름을 붙인 툴 등록, 원래 이름으로 실행 요청이라는 핵심 구조를 따른다.

DSH는 SDK의 검증을 더 세밀하게 통제하려고 저수준 `client.request()`를 사용한다. 여기서는 SDK 1.30.0의 `listTools()` / `callTool()`을 사용한다. DSH의 lifecycle/reconnect/output projection 전체를 복제한 것은 아니다.

## 기본 서버

| 서버 | 연결 | 용도 | 확인한 툴 수 |
| --- | --- | --- | --- |
| filesystem | stdio, 공식 npm 배포 | 제한된 폴더의 파일 생성/조회 | 14 |
| memory | stdio, 공식 npm 배포 | 개체/관찰 정보 저장·검색 | 9 |

| cloudflare | `https://docs.mcp.cloudflare.com/mcp` | Cloudflare 문서 검색 | 2 |

설치한 패키지:

- `@modelcontextprotocol/sdk`: 1.30.0
- `@modelcontextprotocol/server-filesystem`: 2026.8.31
- `@modelcontextprotocol/server-memory`: 2026.8.31

원격 서버는 이번 테스트에서 인증 없이 연결/호출됐으며, 외부 서비스 가용성이나 툴 목록은 바뀔 수 있다. 원격 서버에는 해당 툴에 보낸 검색어/인자만 전송한다. 세션 전체나 LLM API 키를 MCP에 보내지 않는다. stdio 자식에는 SDK의 기본 환경과 명시적인 설정만 전달하며 process.env 전체를 전달하지 않는다.

## 저장 위치와 테스트 프롬프트

Filesystem 접근 범위: `<작업폴더>/.my-first-harness/mcp-files/`만 허용. 이 폴더는 gitignore에 추가했다. 기존 내장 filesystem/shell 툴의 권한을 제한하는 변경은 아니다.

Memory 데이터: `~/.my-first-harness/mcp/memory.jsonl`. 프로젝트 간 공유하는 별도의 MCP 메모리이며 세션 history/압축과는 독립적이다.

실행: `node my-first-harness.ts`.

예시:

```text
MCP filesystem의 list_allowed_directories로 허용된 폴더를 확인하고,
그 안에 hello.txt를 'Hello MCP!' 내용으로 만들어서 다시 읽어줘.
내장 파일/터미널 툴 대신 mcp__filesystem__ 툴을 써.

MCP memory에 이름 'MCP 테스트', 종류 'experiment', 관찰 '좋아하는 색은 파랑'을
저장하고 검색해서 확인해줘.

Microsoft MCP로 TypeScript 관련 문서를 찾아줘.

Cloudflare MCP로 Workers가 무엇인지 검색해서 두 문장으로 설명해줘.
```

## 검증

- `pnpm test`: 기존 16개 + MCP/스키마 7개, 총 23개 통과.
- `pnpm --package=typescript dlx tsc --noEmit`: 통과.
- `pnpm test:mcp`: 실제 서버 네 개 연결 및 28개 툴 등록. 파일 쓰기/읽기와 범위 밖 접근 거부, Memory 저장/조회 및 JSONL 저장, Microsoft/Cloudflare 검색 확인.
- 실 서버 smoke test는 임시 프로젝트/임시 사용자 홈을 사용한다. 생성한 임시 데이터만 테스트 후 정리한다. 실제 사용자 메모리는 변경하지 않는다. LLM/API 키 없이 실행되며 원격 MCP 네트워크는 사용한다.
- 실제 CLI + 현재 LLM에서도 `mcp__filesystem__list_allowed_directories`와 `mcp__cloudflare__search_cloudflare_documentation` 요청 → 두 tool 결과 기록 → 최종 답변 확인. `/quit` 종료 코드 0 확인.
- Cloudflare는 JSON Schema 2020-12, 로컬 서버는 draft-07을 사용했다. `tool-schema.ts`에서 두 검증기를 구분해 원본 스키마를 유지한다. 모든 JSON Schema 규격을 지원한다는 뜻은 아니다.

## Bun 배포 주의

하네스 실행파일과 외부 stdio MCP 서버는 별개 프로그램이다. 로컬 MCP 두 개는 Node.js와 설치된 npm 패키지를 필요로 하며 이번 실행파일에 함께 내장하지 않았다.

Bun 빌드 후 프로젝트 디렉터리에서는 네 서버가 연결됐다. 패키지가 없는 배포 환경에서는 로컬 서버 설정을 안내 후 건너뛰고 HTTP 서버는 계속 연결하도록 처리했다. 로컬 MCP까지 포함하는 독립 배포 패키징은 이번 범위가 아니다.

README와 provider 코드는 변경하지 않았다.
